## Disagreement, not a reason to tune
C17 asks certify_active_ports=True. Original private oracle expected REJECT_SCOPE. Implementation emits ASK with runtime_certification UNKNOWN. Protocol-v2 explicitly specifies this ASK behavior before execution. Neither the input boolean nor catalog determines whether the request means 'certify now using only the permitted static evidence' or 'retain this objective and ask what evidence is needed.' Those are different decision contracts.

The rejection interpretation is appropriate if certification is a mandatory deliverable within this static-only session: this evaluator cannot perform it, and no user-provided assertion can turn static metadata into observed activation. REJECT_SCOPE then means refusal of an unsupported action, not proof the ports cannot activate.

The clarification interpretation is appropriate for an iterative specification assistant: activation truth is unknown, the requirement can be retained, and the assistant can ask whether to revise certification scope or obtain a separate permitted runtime assessment. ASK must not imply that more configuration text alone can certify activation. This was the explicit protocol-v2 interpretation, and the recorded blocker says to revise the request or supply separate evidence.

Recommendation: retain ASK as protocol-consistent for this recorded experiment, retain REJECT_SCOPE as original oracle expectation, and mark the original acceptance disagreement unresolved by the raw input. Do not award a perfect original score by changing the contract after seeing results. The oracle is a fallible operationalization of intended semantics, not behavioral ground truth; implementation/protocol agreement likewise does not prove the protocol is optimal. Pre-execution reconciliation of action semantics was incomplete despite author/implementation separation.

Separate epistemic status from permitted action. Keep runtime activation UNKNOWN in both interpretations. Add explicit request fields such as deliverable_scope=static_only/runtime_evidence_required and deferral_allowed. If runtime certification is mandatory now with no authorized runtime evidence channel, REJECT_SCOPE. If deferral is allowed, ASK whether to retain and defer certification or narrow the deliverable. Do not solicit secrets. Evidence admissibility must specify what counts as runtime evidence; attestations alone are insufficient. Preserve requirement IDs and the runtime obligation through either action. Freeze this distinction and oracle before a future run; no further expansion is recommended for this paper merely to chase a perfect score.

## Static code boundary review: hard failures outside the authored suite
The following are source-inspection counterexamples, NOT executed findings. They limit generality even though the authored checks passed. Do not patch them post-result in this experiment.

1. Unknown intent predicates can silently pass. evaluate reads a fixed set of intent keys and ignores extra keys; e.g. a mandatory unimplemented intent constraint attached to an otherwise grounded state would not cause UNKNOWN. Unknown route values do cause intent_predicate_unknown, but there is no closed-schema validator. Therefore 'unimplemented predicates remain unknown' holds only within the recognized DSL, not for arbitrary extensions. This is a hard failure if the API accepts such extensions as requirements; outside-schema inputs must be rejected/unknown under a future explicit validation contract.
2. Multi-step route witness mismatch. Through-Agent checks independently seek ChatInput -> chosen Agent and chosen Agent -> ChatOutput. They do not enforce the intended output name response, reject bypass paths, or require a single designated input/output session. A compatible edge from Agent.structured_response can satisfy the role check, and different chat endpoints can witness the two halves. These checks establish limited local route existence, not exclusive routing, message semantics, or shared conversation identity. Such stronger intents must not be inferred as satisfied.
3. Ambiguous revisions may be applied before conflict checks. Rename preconditions require old identity present and new absent, but not uniqueness or consistency of old node assertions. route_through_agent similarly chooses nodes via a last-write-wins dict before conflicting node records are diagnosed. A patch could therefore be applied to an identity-conflicted state and only afterward return ASK. If contract requires no mutation until identity is settled, this is a hard failure outside covered cases. Patch transactionality across all blockers is not guaranteed.
4. Duplicate node IDs with different types can make downstream checks order-sensitive: nodes dict chooses the last type. node_type_conflict is retained, but port/blocker details can differ under permutation. The tested conflict fixture uses separate node_type_assertions, not conflicting duplicate node records. Identical binding duplicates are safe for action sets; complete evidence lists/post_state intentionally retain duplicates and are not fully canonicalized.
5. Binding conflicts are only recognized as simultaneous attested/revoked states. Multiple different positive binding identities/values on the same field are not checked for exclusivity. Whether that is a true conflict requires a cardinality/binding identity contract absent from this schema. Shared witness IDs across distinct nodes are not globally validated. Rename updates scoped node references, not opaque evidence IDs; that is correct for this schema but does not handle arbitrary embedded references.
6. Unknown binding states/tiers fail required-field satisfaction, but do not receive a precise independent unknown diagnosis; orphan node_type_assertions are ignored. Unknown top-level structures are not validated. Unsupported/malformed data can raise exceptions rather than return an explicit unknown decision.
7. Revoke_model on any existing node is accepted, even a non-Agent or a node with no model field. The tested operation is Agent-specific. General admissibility needs schema/type preconditions. remove_node outside the conflicting-through-Agent case is intentionally unimplemented and remains UNKNOWN; this is a limit, not hidden support.

These source-level risks must be disclosed as bounded DSL/input validation and revision/route limitations. They do not invalidate the measured 24-case action agreement, but do preclude a general conformance or safe generator claim. Freeze this study as-is, publish the limits, and do not enlarge the suite or tune implementation to improve the headline.
