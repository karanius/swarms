## 8. Test Design and Evaluation Protocol

Verification separates implementation correctness from scientific generalization. The experiments use saved source data; no workflow, model call or task-success experiment is run.

| Check | Evidence / outcome | What it cannot establish |
|---|---|---|
| Controlled neighborhood checks | 9 passed: separate centers, binary duplicate edges, shared neighbors, unknown exclusions, zero-degree handling, no invented inactive outputs, hand-counted confidence/lift, all-origin grouping, engine reference counts | Reliability over every possible export |
| Existing extraction checks | 8 passed for the prior topology extractor | Active outputs or runtime validity |
| Separate catalog recount | 890 rules recounted | Unseen-family prediction |
| Actual preview-edge audit | 62,265 previews across 981 source graphs checked | Behavioral correctness |
| Freeze check | Topology index and aggregate graph-file digest match | Authenticity beyond the archived provenance |
| Frontend build / browser checks | Recorded in the delivery evidence after interaction verification | User comprehension or general performance benchmarks |

All examples are exposed for exploration. A future generalization experiment needs newly frozen source families and a separate tuning/evaluation policy; these exploratory results must not be relabeled held out.

### Boundary-stage verification

Eight controlled tests check incoming/internal/outgoing partitioning, disconnected required fields, potential terminal outputs, occurrence aliasing and one-hop expansion, cycle/disconnection detection, unknown edges, empty selection/source immutability, and parallel edges. A separate audit applies independent endpoint predicates to every edge in 445 representative graphs/seeds, confirms witness inclusion and member identity, and retains every source origin. This covers one ranked representative per unordered pair, not all occurrences or arbitrary edited selections. Browser checks cover selection, expansion/reset, purpose editing, source disclosure, search and notebook embedding. These are engineering checks; they do not constitute independent evaluation of composite usefulness.

### Study C masking, measures and verification

There are 402 deterministic masked cases among assessment neighborhoods with at least two features. Each target is chosen by a stable case/feature hash; all copies of its feature are removed. A fixed1000-case cap was not reached. 167 targets occur in training vocabulary; the other 235 remain in the denominator. The 308 other assessment neighborhoods are not scored in this task. No behavioral negatives are created from missing saved edges.

| Check | Implemented verification |
|---|---|
| Rule and graph isolation | Same-X language allowlist; source-family partition; original occurrence IDs |
| Native application | Native candidate sets/scores compared against direct one-body application for every rule arm/case |
| Source fidelity | Rebuild every transaction from original extracted edge witnesses and verify frozen derived-file hashes |
| Counts and comparisons | Independent training support/lift, train-only guidance, all four arms and rate/macro denominators |
| Proposed designs | Training-only descriptors/origins, exact body/head signatures, required exposures, resource fields and type judgments |
| Robustness tests |12 contract tests, including16-answer regression and stale-output rejection |
| Verifier challenge | Eight deliberately corrupted artifacts must be rejected |

Overall recovery divides by all 402 cases; answered-only recovery divides by the arm's answered cases. Macro-family recovery averages the case fraction within each represented group; source groups do not establish independence. No significance or generalization claim is made. A different top prediction can be a plausible alternative even when it does not recover the one saved target.

### Study D: prospective authored conformance protocol

Study D uses synthetic intent/configuration/graph states, not retrospectively assigned purposes for corpus examples. The coordinator authored 24 cases before ledger implementation, following a jointly debated blueprint, and withheld expected decisions outside the implementation workspace. This is internal author/implementation separation, not external academic evaluation or unseen real-task generalization. Eight three-case families cover required configuration, structural obligations, unsupported capabilities, conflicting information, identity revisions, evidence boundaries, retained intent and mixed controls.

Each input identifies node occurrences, port-labeled edges, scoped binding assertions, explicit intent requirements and an optional authorized revision. The tested transition is an incomplete specification to a statically grounded specification, a precise question, an authorized patch or a scoped rejection. `SPEC_GROUNDED` remains conditional on synthetic assumptions and retains runtime unknowns. B0/B1 passes are assessed only on their declared ports/required-fields coverage, not as readiness decisions.

For each base case the notebook also constructs a bijective node-ID rename, list-order permutation and duplicate-identical-binding variant: 96 states and 288 method decisions. These transformations test invariance; they do not create 96 independent observations. The separately written coordinator checker examines required blocker sets, allowed patch scope, runtime unknowns, unchanged-state conditions, native metadata required-field/type predicates on successful decisions and metamorphic action/blocker consistency. The coordinator additionally reports exact reproduction of all 72 base-case method decisions from frozen sources.

Acceptance is reported against the original oracle, including disagreement. `inputs/verification-v2.json` preserves 927 assertions and four C17 representation-level action mismatches. Seven deliberately corrupted result variants each produced additional detected failures in checker sensitivity testing. A checker path-resolution issue and malformed-patch handling crash were corrected before the final recount; no ledger predicates or first results changed. These checks assess engineering sensitivity, not runtime validity or completeness. Source-inspection counterexamples beyond the authored suite remain explicitly unexecuted limitations, not additional measured test failures.

### Study E checks and stopping rules

This is a coauthored development example, not an evaluation sample. The native builder produced real static node/edge JSON; the higher grouping, purposes and policies were authored and normalized. The checker verifies reference identity, native fields/handles/type overlap, the specimen's DAG policy, exact induced/crossing wires, public input/output declarations, lower/scoped obligation retention, configuration ownership, handoff order, requirement references, and no runtime promotion.

The final finite check performs 139 assertions per revision, with 10 open obligations. Nineteen deliberately corrupted artifacts test sensitivity to specified errors; four test methods cover the positive case, corruption family, revision footprint, and finite stage gates. These are engineering coverage counts, not independent observations, success rates or significance estimates. Early checks missed scoped-obligation retention, configuration ownership and order compatibility; fault injection and a separate source reviewer exposed them, and the checker was repaired before final recount. Preserve those corrections as development history.

The deterministic trace inspects authored decompositions top-down, checks the saved native witness bottom-up, and stops with questions. It does not infer the hierarchy from a request autonomously. An explicit finite budget and repeated-state guard prevent endless gate traversal. Invalid structure stops with rejection. Passing the structural gate does not resolve purpose, runtime, policy or human authority.
